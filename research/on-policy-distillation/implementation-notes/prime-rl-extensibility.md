## A. Current OPD Implementation

### A1. How does `compute_teacher_logprobs()` work?

**File:** `src/prime_rl/orchestrator/utils.py:146-176`

```python
async def compute_teacher_logprobs(
    clients: list[vf.ClientConfig],
    model_name: str,
    samples: list[TrainingSample],
) -> list[list[float]]:
    """Compute teacher model logprobs for a batch of training samples via prefill."""

    async def _compute_single(client_config: vf.ClientConfig, sample: TrainingSample) -> list[float]:
        client = setup_openai_client(client_config)

        async with await get_semaphore():
            response = await client.post(
                "/chat/completions/tokens",
                body={
                    "model": model_name,
                    "messages": [{"role": "user", "content": ""}],
                    "tokens": sample.prompt_ids + sample.completion_ids,
                    "max_tokens": 1,
                    "temperature": 1.0,
                    "top_p": 1.0,
                    "skip_special_tokens": False,
                    "prompt_logprobs": True,
                },
                cast_to=ChatCompletion,
            )
        return [
            0.0 if lp is None else float(next(iter(lp.values()))["logprob"])
            for lp in getattr(response, "prompt_logprobs", [])
        ]

    return await asyncio.gather(*[
        _compute_single(client, sample)
        for client, sample in zip(cycle(clients), samples)
    ])
```

**Key observations:**

1. **The teacher receives the EXACT SAME token sequence as the student.** It sends `sample.prompt_ids + sample.completion_ids` -- the student's prompt tokens concatenated with the student's completion tokens.

2. **It uses the `/chat/completions/tokens` custom endpoint** (not standard OpenAI API). This endpoint accepts raw token IDs and returns `prompt_logprobs` -- the per-token log-probabilities of each token in the input sequence under the teacher model.

3. **The teacher CANNOT receive a different prompt than the student** with the current implementation. The function only takes `TrainingSample` objects that already have their token IDs fixed. There is no mechanism to pass an alternative prompt or additional context.

4. **It returns ONLY the logprob of the actual token at each position** (sampled-token logprob). The line `float(next(iter(lp.values()))["logprob"])` extracts a single scalar from the `prompt_logprobs` dictionary at each position. There is no full-vocabulary logit distribution.

5. **The dummy message `{"role": "user", "content": ""}` is passed** because the endpoint requires a messages field, but the actual tokens come from the `tokens` field which overrides the tokenized messages.

### A2. How is the teacher KL computed in the loss function?

**File:** `src/prime_rl/trainer/rl/loss.py:107-173`

```python
teacher_kl = teacher_logprobs - trainer_logprobs if teacher_logprobs is not None else None
# ...
advantages = loss_config.adv_tau * advantages
if teacher_logprobs is not None:
    advantages = advantages + loss_config.teacher_tau * teacher_kl.detach()
coeff = importance_ratio * (advantages - loss_config.kl_tau * log_importance_ratio)
loss = -(coeff.detach() * trainer_logprobs)[keep_mask].sum()
```

**Key observations:**

1. **The teacher KL is `log p_teacher - log p_student` (reverse KL direction).** This is computed ONLY on the sampled tokens (not full vocabulary).

2. **The teacher signal is added to the advantage**, weighted by `teacher_tau`. It is NOT a separate loss term -- it augments the REINFORCE-style advantage signal. The formula effectively becomes:
   ```
   advantage_total = adv_tau * reward_advantage + teacher_tau * (log p_teacher - log p_student)
   ```

3. **This is sampled-token-only KL (reverse KL).** It uses only the logprob of the token that was actually generated by the student. There is NO full-vocabulary JSD or forward-KL computation.

4. **The `.detach()` on `teacher_kl` means no gradient flows through the teacher signal** -- it acts purely as a reward shaping signal.

### A3. How are teacher logprobs threaded from orchestrator to trainer?

**Data flow:**

1. **Orchestrator** (`orchestrator.py:527-537`): After converting rollouts to `TrainingSample` objects, calls `compute_teacher_logprobs()` and assigns the result to `train_example.teacher_logprobs` for each sample.

2. **TrainingSample** (`transport/types.py:5-22`): Has field `teacher_logprobs: list[float] | None = None`. This is a flat list of floats covering the FULL sequence (prompt + completion). It uses `msgspec.Struct` for fast serialization.

3. **TrainingBatch** (`transport/types.py:25-30`): Contains `examples: list[TrainingSample]` -- just a list of samples with step metadata.

4. **Packer** (`trainer/rl/packer.py` and `trainer/batch.py:6-59`): `prepare_sample()` passes `teacher_logprobs` through directly to `MicroBatch`. If the sample is truncated to `seq_len`, teacher_logprobs are also truncated.

5. **MicroBatch** (`transport/types.py:34-50`): Has field `teacher_logprobs: list[float] | None = None`. During sequence packing, teacher_logprobs are concatenated across packed samples (batch.py:104-107).

6. **DataLoader** (`trainer/rl/data.py:175-198`): Converts `MicroBatch.teacher_logprobs` to a `torch.Tensor` (or None).

7. **Trainer** (`trainer/rl/train.py:316-318`): Reads `teacher_logprobs` from micro_batch, moves to CUDA, passes to `compute_loss()`.

## B. Extensibility for Privileged-Info Self-Distillation

### B1. Where would you modify the code to give the teacher a different prompt?

**The core problem:** `compute_teacher_logprobs()` sends `sample.prompt_ids + sample.completion_ids` to the teacher. For privileged-info self-distillation, the teacher needs to see a DIFFERENT prompt (e.g., one that includes the ground-truth answer) while evaluating the SAME completion tokens.

**Full data flow to modify:**

1. **Environment/Dataset level**: The ground-truth answer must be available in the orchestrator. Currently, `vf.RolloutOutput` contains `example_id` and the environment has access to the dataset, but after rollout completion the ground-truth is not propagated into the `TrainingSample`.

2. **Orchestrator** (`orchestrator.py:486-537`): The `interleave_rollout()` function creates `TrainingSample` objects. Teacher logprobs are computed AFTER this conversion. This is where the modification point is.

3. **`compute_teacher_logprobs()`** (`orchestrator/utils.py:146-176`): This function would need to accept teacher-specific token sequences instead of deriving them from `sample.prompt_ids + sample.completion_ids`.

**Modification approach:**

The cleanest approach would be:

(a) **Add a `teacher_prompt_ids` field to `TrainingSample`** (or pass it alongside):
```python
class TrainingSample(msgspec.Struct, ...):
    # ... existing fields ...
    teacher_prompt_ids: list[int] | None = None  # NEW: alternative prompt for teacher
```

(b) **Modify `compute_teacher_logprobs()`** to use `teacher_prompt_ids` when present:
```python
async def _compute_single(client_config, sample):
    teacher_prompt = sample.teacher_prompt_ids or sample.prompt_ids
    response = await client.post(
        "/chat/completions/tokens",
        body={
            "tokens": teacher_prompt + sample.completion_ids,
            # ... rest unchanged
        },
    )
    # Return only completion logprobs (offset by len(teacher_prompt))
    all_logprobs = [...]
    return all_logprobs  # May need alignment logic
```

(c) **Populate `teacher_prompt_ids` in the orchestrator** before calling `compute_teacher_logprobs()`. This requires tokenizing a different prompt for the teacher (e.g., the student prompt + the ground-truth answer appended).

### B2. Does TrainingSample have room for extra metadata?

**File:** `transport/types.py:5-22`

`TrainingSample` is a `msgspec.Struct` with `omit_defaults=True`. Adding new optional fields with `None` defaults is straightforward and backward-compatible:

```python
class TrainingSample(msgspec.Struct, array_like=True, gc=False, omit_defaults=True):
    # ... existing fields ...
    teacher_prompt_ids: list[int] | None = None
    metadata: dict | None = None  # generic metadata bucket
```

However, `TrainingSample` is serialized across process boundaries (orchestrator -> packer -> trainer). Adding large data (like full ground-truth text) would increase serialization overhead. The `teacher_prompt_ids` approach is more efficient since you only add the tokenized teacher prompt, and only when needed.

**Important constraint:** `TrainingSample` uses `array_like=True` in msgspec, which means fields are serialized positionally. New fields MUST be added at the END with defaults to maintain backward compatibility.

### B3. How does the orchestrator access environment info?

**File:** `orchestrator.py:161-170`

The orchestrator loads environments via verifiers:
```python
train_env_group = vf.EnvGroup(
    envs=[vf.load_environment(env_id, **env.args) for env_id, env in zip(env_ids, config.env)],
)
```

The dataset is accessed through:
```python
train_dataset = train_env_group.get_dataset(seed=config.buffer.seed)
```

The rollout output (`vf.RolloutOutput`) includes:
- `example_id`: identifies which problem this is
- `trajectory`: list of steps with prompts and completions
- `reward`: the score
- `task`: environment identifier

**The ground-truth answer is available in the environment's dataset.** The buffer stores examples from the dataset, and each rollout's `example_id` maps back to a dataset row. However, the ground-truth is NOT currently propagated through to `TrainingSample`.

**To access ground-truth at teacher-logprob-computation time**, you would need to:
1. Either pass the dataset/buffer reference to the `compute_teacher_logprobs` call
2. Or pre-compute and cache the teacher prompt tokens alongside each training sample

### B4. What would a minimal diff look like?

```python
# ---- transport/types.py ----
class TrainingSample(msgspec.Struct, array_like=True, gc=False, omit_defaults=True):
    # ... existing fields unchanged ...
    teacher_prompt_ids: list[int] | None = None  # NEW

# ---- orchestrator/utils.py ----
async def compute_teacher_logprobs(
    clients: list[vf.ClientConfig],
    model_name: str,
    samples: list[TrainingSample],
) -> list[list[float]]:

    async def _compute_single(client_config, sample):
        client = setup_openai_client(client_config)
        # Use teacher prompt if available, otherwise fall back to student prompt
        prompt_ids = sample.teacher_prompt_ids if sample.teacher_prompt_ids is not None else sample.prompt_ids
        tokens = prompt_ids + sample.completion_ids
        async with await get_semaphore():
            response = await client.post(
                "/chat/completions/tokens",
                body={
                    "model": model_name,
                    "messages": [{"role": "user", "content": ""}],
                    "tokens": tokens,
                    "max_tokens": 1,
                    "temperature": 1.0,
                    "top_p": 1.0,
                    "skip_special_tokens": False,
                    "prompt_logprobs": True,
                },
                cast_to=ChatCompletion,
            )
        all_logprobs = [
            0.0 if lp is None else float(next(iter(lp.values()))["logprob"])
            for lp in getattr(response, "prompt_logprobs", [])
        ]
        # Return logprobs for the full sequence (prompt + completion)
        # The teacher logprobs cover a potentially different-length prompt
        return all_logprobs

    return await asyncio.gather(*[
        _compute_single(client, sample)
        for client, sample in zip(cycle(clients), samples)
    ])

# ---- orchestrator/orchestrator.py (in the process_rollout section) ----
# After creating train_examples, before compute_teacher_logprobs:
# For each training example, build the teacher prompt with privileged info
if config.teacher_model and teacher_inference_pool:
    for train_example, rollout in zip(train_examples, train_rollouts):
        # Build teacher prompt with ground-truth appended
        gt_answer = get_ground_truth(rollout["example_id"], train_dataset)
        teacher_prompt = build_teacher_prompt(
            student_prompt_ids=train_example.prompt_ids,
            ground_truth=gt_answer,
            tokenizer=tokenizer,
        )
        train_example.teacher_prompt_ids = teacher_prompt
```

**Critical alignment issue:** When the teacher sees a different prompt, the teacher's `prompt_logprobs` will have a different length for the prompt portion. The completion tokens are the same, but the prompt prefix is different. The existing code expects `teacher_logprobs` to cover the full sequence `prompt_ids + completion_ids`. With a different-length teacher prompt, you need to extract only the completion portion of the teacher's logprobs and then prepend zeros for the student's prompt portion.

This alignment logic is the trickiest part:
```python
# Teacher returns logprobs for: teacher_prompt_ids + completion_ids
# We need logprobs for: student_prompt_ids + completion_ids
# So: take the last len(completion_ids) logprobs from teacher
# And prepend len(student_prompt_ids) zeros
teacher_completion_logprobs = all_logprobs[len(prompt_ids):]  # completion part only
teacher_logprobs_aligned = [0.0] * len(sample.prompt_ids) + teacher_completion_logprobs
```

## C. Extensibility for SDPO-Style Reprompting

### C1. Can the orchestrator access other rollouts' results within the same batch?

**Yes, but only AFTER all rollouts in the batch complete.** The orchestrator workflow is:

1. `scheduler.generate_batch()` generates ALL rollouts for the batch (`orchestrator.py:454-456`)
2. Advantages are computed across all rollouts (`orchestrator.py:462-470`)
3. Teacher logprobs are computed (`orchestrator.py:526-537`)

At step 3, you have access to ALL rollouts in `train_rollouts` and all `train_examples`. So you CAN look at other rollouts' results (rewards, completions) when constructing teacher prompts.

### C2. Is there a concept of "rollout groups"?

**Yes.** The `rollouts_per_example` config parameter groups rollouts by problem:

- `config.rollouts_per_example` specifies how many rollouts per problem (`orchestrator/config.py:764-770`)
- Rollouts are ordered: first N rollouts are for problem 1, next N for problem 2, etc.
- `compute_advantages()` groups by `samples_per_problem` (`advantage.py:65-91`)
- `example_id` field identifies which problem each rollout belongs to

**So finding successful peer solutions is possible:** After rollout completion, iterate over all rollouts, group by `example_id`, and identify which ones have `reward > 0`.

### C3. Where to inject reprompting logic?

The ideal injection point is between rollout completion and teacher logprob computation (`orchestrator.py:525-537`):

```python
# AFTER: train_examples are created and advantages computed
# BEFORE: compute_teacher_logprobs is called

# INJECTION POINT: Build SDPO-style teacher prompts
if config.teacher_model and teacher_inference_pool:
    # Group rollouts by example_id
    rollout_groups = group_by_example_id(train_rollouts, train_examples)
    for example_id, (rollouts, examples) in rollout_groups.items():
        successful = [r for r in rollouts if r["reward"] > 0]
        for example in examples:
            teacher_prompt = build_sdpo_teacher_prompt(
                student_prompt_ids=example.prompt_ids,
                peer_solutions=successful,
                error_messages=...,  # from environment feedback
                tokenizer=tokenizer,
            )
            example.teacher_prompt_ids = teacher_prompt

    # Then proceed with existing compute_teacher_logprobs call
```

## D. Extensibility for Auxiliary Losses

### D1. How is the loss function structured?

**File:** `trainer/rl/loss.py:193-252`

The loss is computed in `compute_loss()`:
- It iterates over packed sequences (one sample at a time within a micro-batch)
- For each sample, it calls `loss_fn(inputs: LossInputs) -> LossOutputs`
- The `LossOutputs` contains a scalar `loss` and a `metrics` dict
- Losses are summed and scaled by `loss_scale`

The loss function is set up via `setup_loss_fn()` which supports either the built-in `default_loss_fn` or a `CustomLossConfig` that dynamically imports any Python function.

### D2. Can additional loss terms be added?

**Via custom loss function (clean extension point):**

The `CustomLossConfig` mechanism (`trainer/rl/config.py:76-82`, `loss.py:176-190`) is the intended extension point:

```toml
[loss]
type = "custom"
import_path = "my_module.my_loss_with_auxiliary"
kwargs = { feedback_weight = 0.1 }
```

Your custom loss function receives `LossInputs` which includes `trainer_logprobs`, `inference_logprobs`, `teacher_logprobs`, `advantages`, and `loss_mask`. You can compute ANY loss from these inputs.

**LIMITATION for RLTF-FM auxiliary feedback loss:** The `LossInputs` dataclass only carries logprobs and advantages. It does NOT carry:
- Raw logits (needed for cross-entropy on feedback text)
- Additional text data (feedback strings, environment messages)
- Any extra metadata

To add a true auxiliary cross-entropy loss that predicts environment feedback, you would need to:

1. **Extend `LossInputs`** to carry additional data (e.g., feedback token IDs, feedback mask)
2. **Extend the training loop** to pass raw logits to the loss function (currently logits are consumed by `selective_log_softmax` and discarded)
3. **Extend `TrainingSample`/`MicroBatch`** to carry feedback text through the pipeline

This is NOT a trivial extension -- it requires modifying the core trainer loop.

### D3. How are training batches structured?

**TrainingSample** (`transport/types.py:5-22`): Per-sample data with prompt/completion IDs, logprobs, mask, advantages, and optional teacher_logprobs.

**MicroBatch** (`transport/types.py:34-50`): Packed sequence with all samples concatenated. Contains input_ids, loss_mask, advantages, inference_logprobs, teacher_logprobs, temperatures, position_ids.

**Adding extra data (e.g., feedback text) to batches:**
- Add fields to `TrainingSample` (e.g., `feedback_ids: list[int] | None = None`)
- Add fields to `MicroBatch`
- Update `prepare_sample()` in `trainer/batch.py` to propagate the field
- Update `packed_samples_into_micro_bs()` to handle the field during packing
- Update `DataLoader._micro_batch_to_tensor()` to convert to tensor
- Update the training loop to pass to the loss function

This is a moderate effort spanning 5-6 files.

## E. Divergence Functions

### E1. What divergence is used for teacher KL?

**Reverse KL (sampled-token only):**

```python
teacher_kl = teacher_logprobs - trainer_logprobs  # log p_teacher(x) - log p_student(x)
```

This is `D_KL(student || teacher)` evaluated ONLY at the sampled token, not summed over the vocabulary. It acts as a per-token reward signal added to the advantage.

There is NO:
- Forward KL (`D_KL(teacher || student)`)
- JSD (Jensen-Shannon Divergence)
- Full-vocabulary KL computation

### E2. Does the teacher endpoint return full logit distributions?

**No.** The `prompt_logprobs` from vLLM returns only the logprob of each token at its position. From `compute_teacher_logprobs()`:

```python
return [
    0.0 if lp is None else float(next(iter(lp.values()))["logprob"])
    for lp in getattr(response, "prompt_logprobs", [])
]
```

This extracts a single float per token position. The full vocabulary distribution is not returned over the API.

### E3. Would implementing JSD require changes to the vLLM teacher endpoint?

**Yes, significant changes:**

1. **vLLM's `prompt_logprobs`** returns only top-k logprobs (or just the actual token's logprob). Getting the full vocabulary distribution (e.g., 152K tokens for Qwen models) over an HTTP API would be:
   - Extremely bandwidth-intensive (152K floats * 4 bytes * seq_len per request)
   - Not supported by the vLLM `prompt_logprobs` parameter without modification

2. **Alternative approach:** Run the teacher as an in-process model (not via HTTP API). This would require either:
   - A separate forward pass through a teacher model loaded in the trainer process
   - Or a custom vLLM endpoint that computes JSD server-side and returns only the scalar

3. **Practical compromise:** Use the sampled-token reverse KL (already implemented) as an approximation. Full-vocabulary JSD is rarely necessary -- most distillation papers show comparable results with sampled-token KL.

## F. Architecture and Code Quality

### F1. How modular is the codebase?

**Highly modular.** The architecture separates concerns cleanly:

- **Orchestrator** (Python async): Generates rollouts, computes advantages, computes teacher logprobs, sends batches
- **Packer** (single-threaded on master rank): Packs variable-length samples into fixed-length micro-batches
- **Trainer** (PyTorch DDP/FSDP): Forward/backward pass, optimizer step, weight broadcast
- **Inference server** (vLLM): Serves model for rollout generation and teacher logprob computation
- **Transport layer**: Pluggable file-system or ZMQ-based data transport between processes

**Extension points are well-documented:**
- Custom loss functions via `CustomLossConfig` (docs/bring-your-own-algorithms.md)
- Custom advantage functions via `CustomAdvantageConfig`
- Custom environments via the `verifiers` library
- External inference/teacher servers via config

## Difficulty Assessment for Each OPD Variant

### Variant 1: Standard OPD (teacher-student)

| Aspect | Assessment |
|--------|-----------|
| **Difficulty** | Trivial |
| **Lines to modify** | 0 (already implemented) |
| **Status** | Fully supported natively |

Already works out of the box. Set `teacher_gpu_ids`, `teacher_tau > 0`, optionally specify a different teacher model.

### Variant 2: Privileged-Info Self-Distillation (OPSD-style)

| Aspect | Assessment |
|--------|-----------|
| **Difficulty** | Moderate |
| **Estimated lines to modify** | ~80-120 lines across 3 files |
| **Key files** | `transport/types.py`, `orchestrator/utils.py`, `orchestrator/orchestrator.py` |
| **Blockers** | None -- clean extension path exists |

**What needs to change:**

1. Add `teacher_prompt_ids` field to `TrainingSample` (~2 lines in `transport/types.py`)
2. Modify `compute_teacher_logprobs()` to use `teacher_prompt_ids` and handle alignment (~15 lines in `orchestrator/utils.py`)
3. Add teacher-prompt construction logic in orchestrator (~40-60 lines in `orchestrator/orchestrator.py`)
4. Ensure ground-truth data flows from environment dataset to the orchestrator's teacher-prompt builder (~20-30 lines)

**The alignment between teacher and student prompt lengths** is the trickiest part. The teacher's `prompt_logprobs` covers a different-length prefix, so completion logprobs must be extracted by offset.

**Approach: Environment-specific `build_teacher_prompt()` function.** For ARC-AGI, this would take the student prompt and append the ground-truth grid. The tokenizer is already available in the orchestrator.

### Variant 3: SDPO-Style Env Feedback Distillation

| Aspect | Assessment |
|--------|-----------|
| **Difficulty** | Moderate-to-Hard |
| **Estimated lines to modify** | ~120-180 lines across 4-5 files |
| **Key files** | `transport/types.py`, `orchestrator/utils.py`, `orchestrator/orchestrator.py`, custom prompt builder |
| **Blockers** | Requires access to peer solutions and error messages; error messages may not be propagated in current vf.RolloutOutput |

**What needs to change:**

1. Same `teacher_prompt_ids` infrastructure as Variant 2
2. Additional orchestrator logic to:
   - Group rollouts by `example_id`
   - Identify successful peer solutions within each group
   - Extract error messages / feedback from failed rollouts
   - Construct SDPO-style teacher prompts with feedback
3. May need environment changes to expose structured error feedback

**Key risk:** The `vf.RolloutOutput["error"]` field exists but may only contain error type strings, not detailed feedback. The `vf.RolloutOutput["trajectory"]` contains full conversation history which may include error messages from multi-turn environments.

**The rollout group structure already exists** via `rollouts_per_example` -- this makes finding peer solutions straightforward.

### Variant 4: RLTF-FM Auxiliary Feedback Modeling Loss

| Aspect | Assessment |
|--------|-----------|
| **Difficulty** | Hard |
| **Estimated lines to modify** | ~200-300 lines across 6-8 files |
| **Key files** | `transport/types.py`, `trainer/batch.py`, `trainer/rl/data.py`, `trainer/rl/train.py`, `trainer/rl/loss.py`, `orchestrator/orchestrator.py` |
| **Blockers** | Requires extending the core trainer loop; custom loss function alone is NOT sufficient |

**Why this is hard:**

1. **The current `LossInputs` dataclass does not carry feedback text.** You need to thread feedback token IDs and masks through the entire pipeline (7 files).

2. **The trainer loop currently discards raw logits** after computing logprobs. An auxiliary cross-entropy loss on feedback text requires the full logit tensor, which means modifying the forward pass handling in `train.py`.

3. **Feedback text has variable length** and needs its own packing/padding logic separate from the main completion.

**Possible simpler alternative:** Implement the feedback modeling as a separate SFT-like loss that shares the same model weights but runs in a separate micro-batch step. This avoids modifying the core RL loss pipeline.

### Variant 5: Full-Vocabulary Logit Distillation (JSD/Forward-KL)

| Aspect | Assessment |
|--------|-----------|
| **Difficulty** | Very Hard |
| **Estimated lines to modify** | ~300-500 lines across many files, plus vLLM modifications |
| **Key files** | `inference/vllm/serving_chat_with_tokens.py`, `orchestrator/utils.py`, `transport/types.py`, `trainer/rl/loss.py`, `trainer/rl/train.py` |
| **Blockers** | Fundamental architectural limitation -- teacher logprobs are computed via HTTP API (single scalar per token), not as full distributions |

**Why this is very hard:**

1. **The teacher runs as a separate vLLM server accessed via HTTP.** Returning full vocabulary distributions (152K floats per token position) over HTTP is impractical for real-time training.

2. **Bandwidth estimate:** For a 2048-token sequence with 152K vocabulary: `2048 * 152000 * 4 bytes = ~1.2 GB per sample`. At 128 samples per batch: ~150 GB per step. This is clearly infeasible.

3. **Alternative: In-process teacher.** Load the teacher model in the trainer process and compute JSD during the forward pass. This requires:
   - Loading a second model in GPU memory (may not fit)
   - Running two forward passes per training step
   - Completely different architecture from the current HTTP-based teacher

4. **Alternative: Server-side JSD.** Modify the vLLM endpoint to compute JSD on the server, sending back only the per-token scalar JSD values. This would require custom vLLM kernel work.

**Practical recommendation:** Stick with sampled-token reverse KL (already implemented). Research evidence suggests the gap between full-vocabulary JSD and sampled-token KL is small, especially when the teacher is only moderately better than the student.

## Recommended Implementation Order

1. **Variant 2 (Privileged-Info Self-Distillation)** -- Most impactful for ARC-AGI, moderate effort, clean extension path. Start here.
2. **Variant 3 (SDPO-Style Reprompting)** -- Builds on Variant 2's infrastructure. Add after Variant 2 works.
3. **Variant 4 (RLTF-FM)** -- Consider as a separate SFT-like training step rather than an in-loop auxiliary loss.
4. **Variant 5 (Full-Vocab JSD)** -- Skip unless empirical evidence shows sampled-token KL is insufficient.
